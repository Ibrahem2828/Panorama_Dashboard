# Authentication and Security

## Session lifecycle

1. Browser posts credentials to `/api/auth/login`.
2. The BFF calls `/api/v1/auth/login/` server-to-server.
3. Tokens are stored in `HttpOnly`, `Secure`, `SameSite=Lax` cookies.
4. The BFF obtains `/api/v1/auth/me/` and builds the dashboard session.
5. Protected API calls pass through the contract-bound `/api/backend/...` BFF.
6. A single refresh retry is attempted server-side on 401; rotation updates only HttpOnly cookies.
7. Logout calls the backend when possible and always clears cookies.

The dashboard session state is explicitly `loading`, `authenticated`,
`unauthenticated`, `forbidden`, or `backend_unavailable`. Only 401 redirects to
localized login; 403 renders access denied and availability failures retain the
session cookies and offer a retry.

## Controls

- CSRF origin/referer and double-submit validation.
- CSP nonce generated by middleware.
- HSTS, frame denial, MIME sniffing protection, strict referrer and permissions policy.
- No tokens in localStorage/sessionStorage.
- Request body limit and backend timeout.
- No arbitrary proxy destinations, user-controlled upstream URL, or
  off-contract operation. The BFF accepts only a documented method/path pair.
- Safe error envelope with request correlation.

## Refresh concurrency

Requests carrying the same refresh token are coalesced within one Next.js
process, and each original request can refresh and retry only once. A deployment
with multiple replicas still needs backend refresh-rotation grace/idempotency or
a shared distributed lock for perfect cross-replica coordination; this frontend
does not claim to provide a global in-memory lock.

## Required production checks

- Confirm cookies are `Secure` behind the Coolify HTTPS proxy.
- Confirm trusted proxy/host configuration at Django and Coolify.
- Confirm login, refresh rotation, session invalidation and logout against staging.
- Run OWASP ASVS/API Top 10, DAST and dependency/container scanning.
